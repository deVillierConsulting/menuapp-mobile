One tap → menu created
"Plan this week →" auto-names the menu "Week of Jul 7" and skips the menu-creation form entirely. The picker sheet opens immediately. Zero unnecessary screens before the user is picking recipes.
Sheet anchors the home screen
The recipe picker is a bottom sheet over the dimmed home screen, not a new route. The user never loses their place — closing the sheet always returns to Home. This also means back-swipe on iOS does the right thing naturally.
Done banner timing
The green "Done" banner appears as soon as the meal target count is hit. It persists but doesn't auto-close — let the user add more if they want. Tapping "Done →" closes the sheet and commits.
Counter in header
"Add recipes 4 added" in the sheet header gives constant feedback without requiring the user to count checkmarks. Once the target is met, the unselected rows fade to 40% opacity to signal "you're done, but you can still add more."
Progress starts at 0
When the menu is first created by the picker author, their vote count shows 0 of 4 — they haven't voted yet, they just added recipes. Voting is a separate intentional act. The vote card is shown immediately so they can start.
Menu detail as scoreboard
The menu detail screen is not the primary voting surface — voting happens on Home. The detail is a scoreboard: who voted what, what's passing, what's failing. It's where you go to check status, not to take action.
Vote chip anonymity
Currently vote chips show per-person with initials. Consider whether votes should be anonymous until the menu finalizes — people may vote differently if they know their partner can see in real time. Open design question.
Design decisions
The picker is the only creation step
Previous flow: Home → Groups → Group Detail → "New Menu" button → Menu name form → recipe picker. That's 5 steps before you pick a single recipe. New flow: Home → tap card → picker opens. 1 step. The menu name is inferred from the week; everything else defaults. Name can be edited later from menu detail.
What happens if both partners pick recipes?
Any group member can open the picker and add recipes. Recipes added by others appear immediately in everyone's picker via real-time update (or next load). The "Done" banner counts total recipes in the menu, not just the ones you added. This encourages collaborative curation rather than one person being the "menu setter."
Open: swipe-to-vote vs. button-vote on Home
The current implementation has swipe-right = approve, swipe-left = skip. The mock above shows buttons. For the Home screen redesign (task #59), swipe gestures are the right call — they're faster and the card-stack metaphor is immediately recognizable. The menu detail screen should keep explicit buttons since it's a review context, not a quick-fire voting context.
Open: meal target — who sets it?
Currently the meal target (4 meals/week) is a group setting. The done banner counts against that target. Should the target be settable per-menu? Or per-group? Or just fixed at 4-5? Surfacing this as a picker option adds friction; hardcoding it removes flexibility. Leaning toward group default + a discrete "I want more this week" option in the sheet header.
