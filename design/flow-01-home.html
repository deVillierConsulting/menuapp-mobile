Group creation = paywall
New users hit the monetization gate here, before any value is demonstrated. Consider letting the first group be free — show the loop once, then gate on the second group or advanced features.
One tap to start
Auto-names the menu "Week of Jul 7", skips the form, opens the recipe picker sheet immediately. The only click before you're browsing recipes.
Swipe, not buttons
Right = approve · Left = veto. The button pair took ~25% of screen height that now belongs to the card. Swipe is faster, universally understood, and allows the card to fill the space. Show a one-time hint overlay on first use only.
Dot counter
5 dots below the card, one per recipe in the pool. Green = approved, red = vetoed, orange = current, gray = unseen. Makes progress legible at a glance without a percentage or "X of Y" label reading as a chore.
Tap to flip
Front: photo + name + cuisine + quick meta. Back: description, stats row (cal/time/serves/protein), key ingredients. You can vote from either side — the swipe rails are always present.
Full recipe link
The "+ 8 more" line on the card back links to the full Recipe Detail screen (flow-05). This is not required to vote — it's an escape hatch for people who want the complete picture before committing.
Exhaustion is a real state
Don't dead-end the user. Show what was vetoed and why the menu is short, then give them "Add more recipes →" (opens the picker sheet) and a secondary escape: "Lower meal target". Both are recoveries, not errors.
Who can veto?
Every voter vetoing the same recipe permanently removes it from this week's pool. But a single veto only removes it from your ballot — the other person still sees it. Finalization ignores recipes where at least one person vetoed. Open question: should a solo veto kill a recipe?
Leading so far
While waiting, show the current leaderboard — recipes with both votes first, then 1-vote, then 0. This turns the waiting state from dead time into anticipation. "Remind →" sends a push notification to the partner.
Finalization is automatic
When the last voter finishes, the menu finalizes immediately — no confirm step. The Shop tab badge appears. Home transitions from State 4 to State 5 in real time via websocket or next-open refresh. "Plan next week" restarts the cycle at State 2.
Voting mechanic decisions
Veto, not Skip
Skip was avoidance — a way to defer a decision without taking responsibility for it. Veto is explicit: "I don't want this." It produces better data for the finalization algorithm and forces genuine engagement with each recipe. There's no limbo. A recipe is either approved, vetoed, or unseen (you haven't reached it yet). The dot counter makes this state visible.
Why swipe wins over buttons
Buttons at 48px height each took up ~100px of the 400px usable screen — 25% — before any padding. The card can now be ~240px tall: a big, hungry food photo. The interaction cost of swipe vs. tap is the same, the motor pattern is actually faster once learned, and there's no ambiguity once you've seen the rail labels once.
Card flip is a deliberate slowdown
The front-of-card experience is designed for fast voting — you should be able to go through 5 cards in under a minute on feel alone. The flip is for when you're not sure. By making it a tap rather than a scroll, the card back feels like a separate decision context, not a continuation of the same screen. After reading the back, you swipe — same mechanic, no mode change.
Veto rule: scales with group size
2–3 members: one veto kills the recipe. This is intentional — the mechanic should be powerful at small group sizes. The philosophy is that it's easy to hop on and add a big pool of good-looking recipes, then swipe fast. With a large pool, a single veto keeps the menu curated without being punishing. 4+ members: majority veto required (more than half the group must veto for a recipe to be excluded). This prevents one person from dominating a larger household's menu. The threshold is derived from the same member count used for approval quorum — the same logic scales both directions.
First-use tutorial: animated demo card
Before the first real recipe card appears, show a single animated demo card with a placeholder recipe. The card auto-drags right (green tint + "YES" label fades in, card flies off), then a second demo card auto-drags left (red tint + "VETO" fades in, card flies off). Total duration ~2.5s, then the real first card slides in. No skip button — it's short enough. This runs once ever, keyed to a "hasSeenVoteTutorial" flag in local storage. Never shown again after the first session.
✓ As Built — account button
A 32×32 Icons.person_outline circle button lives in the top-right of every top bar variant. Tapping it opens a bottom sheet showing the signed-in user's name, email, and a "Sign out" list tile. On the empty-state screens (_NoGroupView, _NoMenuView), the button floats in a Padding+Align at the top of a SafeArea column, with the content centered below in an Expanded.
✓ As Built — voting screen background
The home voting screen uses the same dark AppColors.ink (#1C1917) background as the onboarding voting screen. The top bar (group name / week label) renders white-on-dark. Full-height cards with gradient photo overlays and ✕/✓ buttons, identical to the onboarding card stack.
✓ As Built — zero states
HomeNoGroup: emoji + "Start planning meals" + "Go to Groups" CTA. HomeNoMenu: emoji + "No menu this week" + "Create a menu" CTA. Both include the account button in the top-right so users can sign out if needed, even with no data.
✓ As Built — multi-group selector
When a user belongs to multiple groups with active menus, a horizontal pill-scrolling ListView replaces the static group name. The active group pill is orange-filled; inactive are outlined. Tapping a pill calls HomeCubit.selectGroup() and updates the card stack in place.
