Browse is grid, search is list
The browse view uses a 2-column photo grid — photos do the selling, you're scanning visually. The search results view switches to a list with tags and metadata — you're evaluating specific candidates, so you need more info per row.
Featured section
The top hero card can be editorially curated (seasonal, trending by group votes, or random from high-rated recipes). For V1 this is just a random high-rated recipe. For V2 it could be personalized to the group's history.
Cuisine filter chips
Chips filter by cuisine tag. Multiple chips can be active simultaneously. The "Quick" chip filters by prep time < 30 min — a non-cuisine filter mixed into the cuisine row. Consider separating these into a full filter sheet for V2 when the library hits 200+ recipes.
"Submit a recipe" surface
The search empty state and the library header both have a "Submit ↗" link. This is the entry point for task #54 (web scraper). For now it can open a form or a URL — just don't dead-end the user when they don't find what they want.
Hero photo is primary
The recipe detail opens to the full-bleed photo and title. The photo is the first thing you see — it has to make you hungry before you read a word. The back button floats over the image as a semi-transparent pill, not a full nav bar, so the photo gets the full canvas.
Segmented body: three views
Ingredients (default) → Steps → Nutrition. All three share the same photo header and "Add to menu" CTA. The segments scroll independently. Starting on Ingredients is the right default — that's the planning view. Steps is the cooking view.
Active step highlight
The current step gets a warm amber background and accent-colored step number. Completed steps get a green check and fade to 50% opacity — they don't disappear, you may want to refer back. Tapping a step marks it done/undone.
Task #33: steps as focusable segments
The steps view is currently a text blob. The structured steps UI shown here (active step, tap-to-advance, strikethrough on done) is task #33. It requires a migration from TEXT to a JSONB steps array in the recipe table.
Design decisions
"Add to this week's menu" as the primary CTA
The recipe detail screen has one job: help you decide if you want this recipe this week. The CTA is anchored at the bottom, always visible regardless of scroll position in the segmented content. Tapping it opens the recipe picker sheet in the context of the current group's active menu — or if no menu exists, prompts to create one.
Recipe ownership is shared, not per-user
All recipes in the library are visible to all users. There's no "my recipes" concept in V1 — the library is global. Recipes submitted via the web scraper (task #54) would initially be private to the submitter's group, then promoted to the global library after a review step. This avoids a two-tier library UX in V1 while leaving a path for V2.
Open: personalization on the browse view
The browse grid currently shows all recipes sorted by… what? Alphabetical is terrible. Options: (a) highest voted across all groups, (b) most recently added, (c) randomized with a weekly seed so it feels fresh, (d) personalized based on group history. For V1, option (c) is easy to implement and doesn't require any ML — the seed ensures both partners see the same "random" order if they browse simultaneously.
Open: recipe photos in the library
The gradient placeholders shown here are standbys. Real food photography is task #21 (AWS) + task #49 (data grooming). Without real photos, the browse grid loses most of its appeal — it becomes a text list with colored boxes. Getting real photos into the library is probably the single highest-impact visual improvement before TestFlight. Spoonacular import is the fastest path.
