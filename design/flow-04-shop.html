Shop tab badge
When the menu finalizes, the Shop tab gets an orange dot badge. This is the only proactive notification the app sends without a push — it's in-app only, visible on the tab bar. The dot clears once the user opens the shop screen.
Grocery CTA on Home
The Home screen's finalized state shows a green "Ready to shop?" card as a more prominent call-to-action than the tab badge alone. Tapping either surface lands on Screen 2.
Categories match store layout
Produce → Meat → Dairy → Pantry → Frozen → Other — ordered the way a standard grocery store is laid out. This isn't alphabetical; it's a shopping route. Aggregated quantities (3 onions across 4 recipes) appear as a single row.
Task #58: categorization
This requires each ingredient to have a category field in the DB. Currently missing. The FDC seed data has category info — it needs to propagate to our ingredient table. Deferred to task #58.
Checked state persists
Checked items stay checked across app backgrounding and re-opening. This is task #57. Stored in the menu's grocery_items table per-user. Closing the app mid-shop and coming back shows exactly where you left off.
Done categories fade
When all items in a category are checked, the category header shows "✓ Done" and the rows fade to 40% opacity. They don't disappear — you may need to uncheck one. This way done sections visually recede without hiding information.
Completion is a moment
Checking the last item shows the completion screen (S4) with a small animation. This is the end of the weekly loop — the reward state before restarting. "Plan next week →" is the primary CTA, which returns the user to Home State 2.
Shared list, async check
Both partners see the same list. If Claire checks off "chicken thighs," Andrew's list updates. No conflict handling needed — checking an item is idempotent. Last check wins; both can shop simultaneously from the same list.
Design decisions
Grocery list is generated from the menu — not manual
The list is always derived from the finalized menu's recipes and their ingredients. Users can't add items manually in V1 — the list reflects exactly what's needed for the week's recipes. This keeps the system clean and avoids the grocery-app problem of lists that never get cleared. Manual additions are a V2 feature once the core loop is solid.
Quantity aggregation is the magic
3 recipes that each use garlic show as "Garlic · 3 heads" not three separate garlic rows. This requires ingredient records to match on a canonical ingredient ID, not a string. Salt/pepper that currently shows as duplicates (bug logged) is a data-quality issue, not an aggregation bug — the fix is canonical ingredient normalization.
Open: async generation timing
Currently the grocery list is generated when the user opens the Shop tab on a finalized menu. Task #17 is to move this to a background job that fires at menu finalization. The user experience difference: with async generation, the list is instant when they open Shop; without it, there's a loading spinner. Worth doing before TestFlight.
Open: what clears the list?
"Plan next week →" starts a new menu cycle. When does the old checked list clear? Options: (a) auto-clear when a new menu is finalized, (b) auto-clear after 7 days, (c) never — archive it. Leaning toward (a) with a 7-day grace period — you might shop Monday and cook Thursday and want to reference the list still. The completed state (S4) is the archive.
